# ABR-T032/T033 — LSASS minidump, user-mode and kernel-attach: detection guidance

Status: `experimental`.

Scope: the CRED task. Both variants produce the same artifact — a
custom-written minidump of LSASS in `%TEMP%\<random>.tmp` (no
dbghelp.dll, no MiniDumpWriteDump, no `comsvcs.dll`MiniDump` chain)
whose path comes back as the task result.

## T032 — user-mode variant

`NtOpenProcess(lsass, PROCESS_VM_READ|QUERY)` → region walk
(`NtQueryVirtualMemory`) → remote-PEB module list →
`NtReadVirtualMemory` per region → minidump writer. Everything rides
the indirect-syscall layer (spoofed stacks), but the operations
themselves are the canonical lsass-read pattern.

### What telemetry remains

| Signal | Where | Notes |
|---|---|---|
| Process access to lsass | Sysmon EID 10 (TargetImage lsass.exe), EDR credential-access sensors, Security 4656 handle audits | THE canonical T1003.001 signal; this variant accepts it as its documented surface |
| Handle open with VM_READ on lsass | handle-audit rules | same |
| The .tmp file write | Sysmon EID 11 in %TEMP% | content matches a minidump regardless of extension (MDMP magic) |
| Exfiltration | beacon result/download chunks + audit log | network side |

### What does NOT fire

- No `rundll32 comsvcs.dll,MiniDump`, no `procdump.exe`, no
  `powershell Get-Process lsass | dump` — none of the tool-specific
  sigma families.
- No dbghelp.dll load into the implant (classic image-load trigger).

## T033 — kernel-attach variant

The iqvw64e call trampoline (T017) performs
`KeStackAttachProcess(lsass)` on the implant's own thread; while
attached the thread's ADDRESS SPACE is lsass's, so the region walk and
every read run as plain user-mode accesses; `KeUnstackDetachProcess`
always precedes any fallible follow-up. **No handle to lsass is ever
opened.** The WinIo physical page-table path is deliberately NOT used
(blacklisted after the reproducible 0x1A/0x61941 bugchecks); only the
proven NtAddAtom trampoline is exercised.

### What telemetry remains

| Signal | Where | Notes |
|---|---|---|
| Vulnerable driver load + Nal device | Sysmon EID 6 (driver load), T013/T017 families | the prerequisite surface (driver staging), not the read itself |
| NtAddAtom content | ETW NT syscall tracing — atoms with unusual sizes | the trampoline's carrier syscall (T017 detection) |
| Kernel pool alloc/free pattern | kernel ETW pool tracing | ExAllocatePoolWithTag with an odd tag, 0x100 bytes, immediate free |
| No lsass signal at all | Sysmon EID 10 stays SILENT | the documented gap: no user-mode handle telemetry exists for an address-space attach |

### What does NOT fire

- Sysmon EID 10 / handle audits: nothing opens lsass.
- The kernel-attach does not create threads in lsass, does not map
  into it, does not write its memory (read-only capture).

## Sigma

T032 is covered by the mature lsass-access families — run the variant
to VALIDATE them. T033 has no direct native-log rule: the guidance is
to alert on the prerequisite chain (revoked-driver device I/O, T017
trampoline atom traffic) and treat "credential data observed in
exercise outcomes with zero EID 10 records" as the coverage-gap
finding for the report.

## Purple-team usage

Run T032, confirm EID 10 + the EID 11 %TEMP% write fire, and map the
timeline against the teamserver audit log. Then run T033 on the same
host: the delta (same credentials, no EID 10) is the concrete
argument for kernel-origin telemetry (ETW pool/atom sensors and
driver-load policy) over purely handle-based lsass protection.
